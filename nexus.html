(01) THE PROBLEM

Every change to the platform’s features & user roles needed a developer

Nexus is built from features. Each feature has roles, which are levels of access: a viewer can only read logs, an editor can change them. RBAC (role-based access control) is the system that stores those roles

  • Admins waited
  • Developers got interrupted
  • More features = more tickets, it didn’t scale

How might we let admins manage features & roles on their own, with no developer in the loop?

(02) THE SOLUTION

Feature Directory

A tab in Nexus’s Admin Console where admins add, rename and delete features and roles themselves, built to take the ticket and the developer out of routine changes

NEXUS ADMIN CONSOLE FEATURE DIRECTORY

(05) DESIGN DECISIONS

A long form added scroll, became difficult to navigate & overwhelming as more roles were created

The intake was split into three steps so that each one asks for a single kind of thinking. A final review step was made mandatory, so everything gets checked once before it goes live.

Delete & rename on every row added visual clutter & increased the chance of accidental deletion

Deletion was placed inside a 3-dot kebab menu, keeping the table clean while making deletion more intentional

A simple confirmation message did not communicate the impact of deleting a feature

An impact-focused modal was introduced to clearly show the affected users, roles, and permissions before deletion
